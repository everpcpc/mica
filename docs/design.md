# Mica design notes

## Purpose

Mica is a macOS Gmail client built with MyGo native UI.
It follows Mimestream's efficient three-pane workflow without copying its branding or assets.
The primary tasks are reading conversations, processing the inbox, and replying quickly.

## Direction

The current message is the focus. The sidebar and conversation list stay quiet and compact.
The sidebar is about 200pt, the list about 340pt, and the reader content is centered and capped at 960pt for comfortable line lengths.
The interface uses the system font, subtle dividers, unread weight and dots, muted avatars, and one blue accent.
The reader uses one continuous theme background across native UI and email WebViews.
Email documents follow live appearance changes through `prefers-color-scheme`, keeping an open message readable without reloading it.
HTML and plain-text bodies have a 24px horizontal reading inset. Root email styles and top-level inline padding take precedence over the HTML default.
Before the first HTML measurement, the body fills the available reader viewport instead of a one-line placeholder. Measurement starts at DOM readiness, and measured or cached heights replace the placeholder.
Subjects, sender metadata, and recipients use a compact Gmail-style hierarchy. Expanded messages offer compact Reply, Reply all, and Forward actions; collapsed messages keep the same actions in one menu. The actions after the conversation still target its latest message.
The reader toolbar floats above the conversation with Liquid Glass tinted toward the theme background so it stays readable over native and WebView content. Primary actions share a blue-indigo gradient and restrained shadow.
Grouped dialog content uses 12pt-radius bordered panels with consistent padding. Conversation rows use rounded selection with a small inset and vertical separation from the list divider.
Reader reply actions use interactive Liquid Glass, and other secondary actions use light borders and shadows. The toolbar Reply shares the same capsule style as the actions after the conversation. On/off settings use native switches with a visible knob. Icon-only toolbar actions and menus use fully circular hover feedback without changing their layout size.
The app icon is a white rounded square with a four-color envelope inspired by Gmail, while the interface keeps its own identity.
English is the source and fallback language, with Simplified Chinese available through MyGo's catalogs.
Gmail sign-in uses the embedded OAuth client by default; a custom client is available in a collapsed section. OAuth tokens are scoped by normalized Gmail email. New logins verify the Gmail identity before committing an account token; the active-account marker changes only during account activation, with `LastAccount` updated after a successful marker write. Reauthorization requires the same email. The marker lives in Keychain independently of SQLite and identifies the latest verified session. Restoration reads the marker first and falls back to `LastAccount` only for legacy installations. Migration verifies the legacy account identity, rebuilds from the formal store, and retires only that legacy token. Adding or reauthorizing an account does not delete the shared legacy token; account removal verifies its ownership before deleting it, the formal token, and local state. Identity checks that may refresh a token run before taking the credential lifecycle write lock; only deletion and marker commits run inside it. Explicit login or recovery may reopen the account only with the current credential generation; service replacement also cancels prior authentication and advances that generation. Authentication callbacks clear their cancel function only when both the service version and their own operation ID still match. Formal credential commits hold the lifecycle lock across reopening, token and marker writes, formal restore, and legacy cleanup; manual Connect, restore, and reauthorization all enter the same generation and operation lifecycle. The HTTP client and Pub/Sub share one token source, and service deactivation covers both paths. Refresh holds the lifecycle read lock and rechecks deactivation before saving so an old service cannot overwrite a newer authorization.
Settings lists saved Gmail accounts for adding, switching, reauthorization, and confirmed removal while retaining one active service, mailbox, and reader. Account activation is a shared asynchronous handoff: restore the target without deactivating the working service, stop and wait for the notification worker, drain the mutation FIFO and cache writes, commit the account markers, then install the target. New composer and mutation entry is closed during the handoff, while label creation and other accepted jobs finish in FIFO order. Cancelling or failing an add or switch preserves the current service and its last-account selection. An open composer blocks account transitions.
Account removal checks the confirmed identity and refuses to delete an account with a local unsent draft snapshot. Both removal paths wait for cache and draft snapshot writes before checking the snapshot or deleting data. Removing an inactive account leaves the active service and marker alone. Removing the active account uses the same handoff and activates the next account with restorable credentials or Demo. With a target account, the active marker is committed before old-account cleanup, and a later cleanup failure is reported without leaving the UI on a partially removed account. Demo fallback completes old-account artifacts before attempting active-marker deletion. Artifact failures keep the current account; marker failures after successful cleanup still move to Demo and report the error instead of leaving the UI on deleted data. Client invalidation and account-directory refresh finish regardless of whether Settings remains open; only Settings widget updates depend on the modal's identity.
Thread summaries, threads, and messages can carry a normalized account email. Single-account views retain raw selection IDs; owner-routed views use a reversible account/thread key and account/message keys for resource state. The account-client registry restores auxiliary services on demand without changing active-account markers, verifies identity and labels before enabling remote draft writes, and assigns generations from one monotonic sequence shared by active and auxiliary accounts. Removal leaves a tombstone so re-adding cannot revive stale callbacks. Async results and cache writes check the owner generation, so replacing or removing one account rejects only its stale work. Local selection uses composite keys while Gmail API calls use raw thread IDs.
All Inboxes appears when at least two saved Gmail accounts exist.
Its disclosure exposes one child per account with an accessible expanded state and a deeper tree level. Choosing a child activates that account and uses the ordinary Inbox query, while choosing All Inboxes keeps the merged projection identified internally by `mail.Unified`. Activation immediately clears the previous projection, and the requested child remains fixed through the handoff and any reauthentication, so intermediate sidebar or keyboard choices cannot replace it. Success preserves the child; removal, failure, or authentication cancellation returns to the current account's ordinary Inbox. Starting a replacement connection or cancelling authentication during removal or Settings closure explicitly clears the pending child request. Collapsing hides only the children, and keyboard navigation skips the hidden rows.
Each account has an independent sorted snapshot, next-page token, merge cursor, and emitted set. A k-way merge orders available summaries by `Updated` with account/thread tie breakers, while loading more consumes cached remainders before fetching only exhausted accounts with a token. Initial and history refreshes start a new merge generation rather than inserting changes into an unstable cursor. Cached snapshots are reused per account; no unified table or merged snapshot is persisted. Local label changes update the complete account snapshots, removals retain account/thread tombstones through page responses and persistence, and Undo reinserts summaries locally before queuing inverse mutations without a history refresh. Network pages preserve same-generation local modifications, and per-account/query write versions prevent older cache jobs from overwriting newer mutations. Cache reads publish values back to the UI thread, and initial and next-page responses validate the owner generation before changing snapshots. Leaving Unified clears composite state; removing an account drops its selection and refreshes the directory, returning to ordinary Inbox when fewer than two accounts remain. Next-page tokens are session-only. Gmail does not promise strict `Updated` ordering across pages, so the merge does not claim a stable server-side global Top-25. Entry and manual refresh update all restorable accounts; system notifications remain active-account only, with no background Pub/Sub workers for inactive accounts.
Unified mutations require an available owner service before optimistic changes. Entering or leaving Unified clears its pending Undo, and Undo restores only summaries that match the current query after applying inverse labels. Mode transitions immediately invalidate the current list request and hide the previous projection and detail cache; a mutation-delayed refresh never exposes merged rows under raw IDs, and delayed label callbacks without a local target do not persist a target-view snapshot. Automatic-read failures restore UNREAD in the original owner/query list and detail caches. List and thread persistence use account/query and account/thread write versions so older work from either view or a stale rollback cannot overwrite newer content. History saves and deletions use the same thread versions and cache-write mutex.
Appearance follows the system unless the user selects Light or Dark. Motion respects Reduce Motion.
The language selector stores locale codes but presents readable names in both its collapsed value and its options.

## Key states

- Without a Gmail connection, a clearly labeled demo mailbox supports the full workflow.
- Label switching, global Gmail search, conversation loading, empty results, request failures, and offline states. When a request fails, the active account can search loaded summaries and bodies locally; this is not a complete Gmail index or an implementation of every Gmail search operator.
- The conversation list can instantly filter to unread threads without changing the Gmail query; opening a thread may remove it from the filtered list while keeping it open in the reader.
- Gmail mailboxes, categories, label visibility, and user labels share one navigation model; internal system labels stay out of the Labels section.
- Label details are fetched individually because the label list endpoint omits message counts.
- Remote images are blocked by default. A message can be allowed explicitly, or automatic loading can be enabled in Settings; per-message permission is session-only, while the global preference persists. The `mica-img` protocol enforces authorization before any remote request, keyed by owner/thread/message, and protocol-relative URLs are normalized to HTTPS. Hidden subtrees do not offer a loading action. Data and Content-ID inline images remain available, and account avatars use a separate loader. Preference writes are awaited before closing the cache. Remote requests never carry Gmail credentials and only connect to public IP addresses; closing a message revokes its tokens.
- HTML email is sanitized with a provider-independent mail sanitizer and rendered in per-message sandboxed WebViews. CSP disables scripts and unproxied subresources, while tables, inline styles, and scoped stylesheets use the browser's real CSS layout.
- Hidden images and tracking images with both dimensions at most 1px are omitted, and narrow readers scale images down proportionally. Hidden inline metadata is removed before document generation and text previews.
- Older read messages in a thread collapse to an accessible sender, preview, and date row; unread and latest messages stay expanded, and manual expansion state follows message IDs.
- The account name and photo come from Google UserInfo. Existing Gmail-only sessions can request the added OpenID scopes once instead of repeatedly prompting.
- Account photos are static; animated images use their first frame without scheduling playback.
- Gmail-style filled importance markers appear in both the conversation list and reader.
- Account metadata, labels, exact query snapshots, loaded conversations, and downloaded attachment bytes are stored in `~/Library/Application Support/Mica/mail.db` through MyGo's SQLite plugin, with account-scoped records and transactional writes. Account deletion removes all of that account's cached data.
- Cached content appears before network revalidation, while fresh in-memory conversations still avoid duplicate requests during the same session. Network failures leave cached content visible, and background body updates preserve the reading position. Offline fallback searches locally loaded summaries and bodies in the active account, with the cache scan performed before publishing the failed request. It does not provide a complete Gmail mirror or complete Gmail search syntax.
- Thread-list and detail snapshots carry revisions allocated by SQLite in the same write transaction. Migration seeds the counter above the largest existing revision before any new write. Offline search reads them in one SQL snapshot and chooses one current summary per thread before filtering rather than merging labels from different snapshots. Legacy mixed-case owner keys and TEXT JSON remain readable. Revision-zero conflicts prefer detail, then use deterministic list query-key order; that fallback does not claim to recover the newest historical write.
- Opening, saving, forwarding, or displaying an inline attachment caches its bytes under an owner/thread/message/attachment key. Inline attachments without a Gmail ID use their position in the message and message-provided bytes before any fetch. Ownerless Demo resources use the active account for cache keys without changing legacy resource identity. Account profile readiness refreshes the loader without replacing open documents, and cache access requires a registered lifecycle. Cache reads, fetches, and writes join the account-transition and quit drains from the start of an operation. Closing the drain rejects new cache work while admitted operations finish. Empty files are valid cached content. Attachments over 32 MiB are not cached; each account retains at most 128 MiB and evicts the oldest saved entries when necessary. Eviction and insertion share one immediate transaction, preserving existing bytes after failure and the quota across concurrent writers. Remote images remain on demand and are not persisted.
- Snooze is a local schedule, not a Gmail date field. Account/thread records contain a wake time and summary in SQLite and are deleted with the rest of that account's cache. The local record is saved before the FIFO removes INBOX; local SNOOZED is only a projection and is never sent as a Gmail mutation. Failed saves or remote changes restore the previous state, including an earlier schedule when one was replaced.
- The Snoozed view merges native `in:snoozed` results, current in-memory rows, cached summaries, and local records in that order, deduplicating by thread and keeping current metadata over fallback records. Local schedules sort before native snoozes without a local wake time, and rows must match Snoozed membership. Startup restoration shares the account-loading job, with a deduplicated follow-up after profile readiness. Timer identity, account generation, restore load, and per-thread local versions prevent stale callbacks from overriding newer actions. Rescheduling invalidates the old timer before the FIFO and installs the new one after success. Waking checks the exact stored wake time, adds INBOX through the owner FIFO, then deletes the record and restores the visible Inbox or Unified stream/tombstone without rebuilding away the restored state. Unsnooze follows the same restore path. Local deletion failure leaves a persistent Restoring record that retries after one minute and resumes cleanup on restart instead of waiting for the original wake time. Offline merges drop local schedules that no longer have a record and exclude Restoring entries from the Snoozed projection. Responses merge with current local summaries on the UI publication path. Ordinary-list Snooze changes invalidate older requests and clear their loading state; current Unified responses continue through the local modification overlay. Background refreshes capture the cache operation before starting work, and owner generation is checked at mutation completion as well as enqueue. Notices are shown only when that owner is visible. Account removal clears that owner's runtime records and timers without deleting other accounts' work. Quit rejects new cache work and waits for admitted cache operations. The email WebView forwards `b` to the same Snooze action as the native shortcut.
- Conversation lists load 25 threads initially and prefetch the next 25 after each successful page. A ready page is consumed only when the list reaches the end, without another request; an in-flight prefetch is never duplicated. Prefetch publication and consumption both check the request and page token, and account or view changes invalidate them. Failed prefetches and initial offline states continue through the full exact cached snapshot or an expanded offline search, filtering already loaded IDs and query mismatches. An empty cached continuation stops further reads until refresh. Snoozed continuation applies the same local-record merge and persists its filtered projection even when it adds no rows. Pagination writes preserve the unvalidated cached tail only while more remote pages exist or offline continuation is active; mutations must not restore removed rows. This remains a progressively loaded cache, not a complete Gmail mirror.
- Opening a conversation synchronizes the reader row before cached or network detail loading. Programmatic opens and `j` / `k` collapse to one selection, while direct list input preserves Cmd/Ctrl, Shift, and select-all multi-selection.
- Selection highlighting is keyed by thread ID and the reader remains a separate identity. Ordinary filtering, pagination, and history prune only selection keys that are no longer visible; Unified history retains off-screen composite selections and the open reader until an explicit removal or account change. Choosing an adjacent conversation after an archive cannot confuse row indices with thread identity.
- Startup and account switches select the newest conversation from the first non-empty list and restore cached detail when available. Later refreshes can insert newer conversations above it without changing the selected thread or switching the reader.
- Closing the main window hides it and keeps Mica in the Dock. Dock activation restores the same window, while Quit still exits.
- Settings opens from the application menu with Cmd+, and the main window is restored when necessary.
- Sidebar and conversation-list widths and the global remote-image preference persist in local preferences and restore before the first frame; per-message image permission and other reading state stay session-only.
- Gmail watch and Pub/Sub Streaming Pull cover only the active account, while notifications remain limited to unread INBOX activity. Shared-subscription messages carry the account email and are acknowledged without triggering history work for other accounts. Each worker owns its stream, timers, and delayed history batches; cancellation discards pending callbacks but keeps running callbacks in the wait set, and account transitions wait for actual exit before replacing state. Notification IDs encode the normalized account email and thread ID, so a click either opens in that account after the shared handoff or is ignored when the target is unavailable. The watch renews daily, and an incremental history reconciliation runs hourly. A per-account local history checkpoint catches up after restarts without treating existing unread mail as new. History additions, deletions, and label changes refresh complete conversations in SQLite before the checkpoint advances. The visible thread list updates without invalidating opened conversations, and selection follows the thread ID when rows move. Draft view and search results always refresh from their own query instead of merging ordinary thread IDs.
- Compose and reply preserve unsent input and attachments after a failure. Multi-file selection and drops read files in the background; each item shows its name, size, reading or error state, and a remove action. Results from removed items or a replaced composer are discarded, and sending is blocked until every attachment has loaded without errors. File selection and drops during send, close, or discard are rejected with an explicit wait message.
- `mailto:` links open an unsent draft without automatically sending or replacing an existing composer. URL parsing preserves literal `+` and percent-encoded recipients, cc, bcc, subject, and body. Cold starts wait for account restoration, startup metadata, and draft snapshots before opening the link. Authentication and account-transition failures resume pending links, and Path recipients are decoded exactly once. The default email app is registered only after an explicit Settings action; status checks and registration run off the UI thread.
- Outgoing attachments are local name, MIME type, and byte data, separate from received attachment metadata. The total limit is 25 MiB (26,214,400 bytes) of unencoded attachment data per message. Each composer reads one attachment at a time and recomputes the remaining allowance before every read, with another total check as results arrive. A read that fails against a stale smaller allowance is retried after loaded items are removed. MIME detection uses the file extension, then content sniffing, with `application/octet-stream` as the fallback.
- The Drafts view uses paginated `drafts.list`, hydrates every item with full `drafts.get`, and forwards the search query. Draft IDs are selection keys while full drafts retain their message and thread IDs. Create and update accept incomplete MIME, including empty recipients and bodies. Sending an existing draft updates its content and then calls `drafts/send`; new messages continue to use `messages/send`, and strict validation happens only at send time.
- Actual composer edits increment the content revision and trigger debounced saves. A separate in-flight flag, independent of the visible save state, allows at most one create or update and rejects duplicate debounces before completion. The returned draft ID is recorded and newer revisions use updates. Empty new composers are not created, while cleared existing drafts are saved as empty; HTML-only content is not treated as empty. Saving, saved, and save-failed states are visible.
- Cancel waits for the latest save and keeps the composer open on failure. If account verification blocks that save, Cancel preserves both the local snapshot and the open composer. Closing an existing draft invalidates its current detail so reopening performs a fresh full get; ordinary readers are unaffected. Composer inputs are disabled while send, close, or discard is pending. Discard waits for any current create or update before deleting; delete failures preserve the draft without leaving saving or actions blocked. Sending also waits for the current create or update before using the latest content, with body, attachments, and draft ID preserved on failure. Reopened drafts restore Bcc, threading, and attachments without adding another reply quote.
- Account-scoped SQLite draft snapshots contain the complete compose snapshot and attachment bytes. Actual edits write the latest snapshot, synchronized saves clear it, and sending or explicit discard also clears it. A successful create immediately records the new draft ID when newer edits remain unsaved. Snapshots restore when the cached account identity matches, including after an offline profile failure, and remain editable offline. Remote draft saves, deletion, and sends wait for a verified account matching both store and recovery identities; an existing or recovered draft never falls back to `messages/send` when this check fails. A recovery account that differs from the current account cannot read, write, delete, or synchronize snapshots. Attachments still being read are restored as explicit errors instead of being omitted.
- Outbox records are separate account-scoped SQLite rows, not Gmail labels or Unified streams. Every send is journaled with its complete Compose payload and attachment bytes before the request, and the linked draft snapshot is updated in the same transaction so recovery cannot create an independent send path. Attempt numbers fence stale writes and deletes, while send and retry work joins the existing account-transition and cache-write drains. Completion removes the row and linked snapshot atomically; a missing row never makes a linked recovery a first send. Discarding completes the local entry before deleting the remote draft and restores it if that remote deletion fails. Entering or leaving Outbox clears the previous projection; local history and Gmail thread-list requests never supply its rows.
- Outbox Message-IDs remain stable across attempts and restarts. A recovered `sending` record becomes `uncertain`; an explicit retry first performs a SENT-scoped `rfc822msgid` lookup and validates the exact message's Message-ID and labels. A match completes cleanup without resending. An empty result requires a second explicit Send again confirmation, and an unavailable lookup blocks retry. Editing after a failed attempt detaches the composer with fresh local and remote draft identities while preserving the original entry. Retrying requires a verified owner, and send/discard operations invalidate older snapshot writes under the same cache mutex used by the writer. Existing Gmail drafts still use `SendDraft`. The send endpoints skip the generic transient retry loop because Gmail offers no idempotency guarantee. The Outbox UI provides a read-only preview, explicit retry, and confirmed deletion for uncertain messages.
- Scheduled sending is a local Mica schedule, not Gmail metadata. The composer offers presets and native date/time controls, rejects past times, waits for pending draft saves, and persists the scheduled Outbox row and linked snapshot before closing. `SendAt` is stored in UTC and displayed in local time. Mica must be running at the scheduled time; overdue records are restored after reopening.
- A scheduled record retains attempt 1 until its first remote send. Only an exact owner/ID/state/attempt/time CAS claim can move it to sending, with Send now bypassing the due-time check and retaining that intent through pre-claim retries. Startup restores schedules across accounts, and timer, restore, owner, and client generations fence callbacks. Claim, remote send, and final state write share one admitted cache-drain operation. Recovered scheduled-origin sending rows become uncertain through a conditional update that cannot recreate a completed row; no uncertain result is automatically resent.
- Scheduled snapshots do not automatically reopen a second composer path on startup, while ordinary uncertain Outbox snapshots retain manual recovery. Cancel schedule invalidates the timer, atomically detaches the linked snapshot and deletes the scheduled row, then restores the complete draft with its draft ID and attachments. Scheduled entries provide Send now and Cancel schedule rather than generic Delete; the restored draft uses the ordinary discard flow. Automatic completion updates only the visible owner's Outbox and never closes an edited or unrelated composer.
- Reply and Reply all take recipients, subject, quote, and threading headers from the selected message. Replies mark their threading as resolved so Gmail and demo services cannot borrow headers from the latest message; legacy unresolved calls retain the fallback. Forward takes its subject, quoted content, and attachments only from that message and starts without a thread ID or reply headers. Conversation-level actions remain wrappers around the latest message.
- Forward attachment sources distinguish local paths from Gmail downloads. Selected attachments load through the same serial composer pipeline as local files; inline `body.data` payloads are copied directly without a fetch, while other attachments use `AttachmentFetcher`. Both paths can populate the bounded attachment cache once read. Download state and storage keys for attachments without an ID use their position in the message.
- Messages with attachments use a `multipart/mixed` outer part. Text and HTML bodies remain nested in `multipart/alternative`; messages without attachments retain their single-body or alternative form. Attachment filenames use RFC encoding, and binary data uses Base64 with lines capped at 76 columns.
- The sidebar Labels section always provides label creation, including when no custom labels exist yet. Right-clicking a custom label opens Gmail-supported color choices and confirmed deletion; color changes use the serial mutation queue and persist with label metadata.
- The reader's native label menu only assigns existing custom labels, shows their current state, and keeps label edits, list membership, and undo consistent.
- Star, archive, trash, spam, and read/unread changes apply locally first and synchronize through a serial background queue. Failures are reconciled with Gmail, and undo restores the local snapshot before queuing the inverse request. Removing the current conversation opens the next one at the same position, or the previous one at the end; the reader clears only when no conversations remain.
- Archive, Trash/Untrash, Spam/Not spam, Star, and Read/Unread resolve action targets in visible-list order; Archive shows the selection count. Mixed Star, Read/Unread, Trash, and Spam selections choose one target state from the first item and skip items already in that state, so Undo never changes items that did not need the action. Single-target actions keep their existing local and remote paths.
- Batch mutations apply local updates once and store ordered undo items in one action. Removal follows the action: never for Star/Read, Inbox and All Inboxes for Archive, all targets for Trash/Spam, and post-action query membership for Untrash/Not spam. Reader replacement follows the original list's next surviving conversation, or the previous survivor when none follows; a reader outside the batch stays open. Undo restores all summaries in one list update and enqueues per-thread inverse requests through the same FIFO. Custom label assignment, replies, and forwards remain scoped to the reader.
- Trash and spam conversations offer Untrash and Not spam based on their actual label IDs, including in search results; the toolbar, application menu, and `#` / `!` shortcuts share this forward/recovery dispatch and menu labels update with the selection. Untrash uses Gmail's dedicated thread endpoint and removes only `TRASH`, while Not spam applies `+INBOX / -SPAM`. Undo records the operation kind so Trash and Untrash reverse through their dedicated endpoints rather than label modification alone. Recovery removes a conversation from a non-search view only when its post-action labels no longer match; search retains the existing remove-and-refresh reconciliation.

## Motion

- Buttons and selection states use MyGo's small, built-in feedback. The unread filter uses a 140ms color transition to a clear Accent active state with a high-contrast icon.
- Loaded conversation content fades in with a 10pt upward movement over 240ms rather than flashing a blank pane.
- The first reader entrance and later conversation transitions use the same short motion. Toasts fade in and out; plain notices remain for 3 seconds, and action notices remain for 5 seconds.
- Message expansion and collapse use an interruptible spring transition. Reduce Motion completes the change immediately.
- MyGo removes or shortens nonessential motion when Reduce Motion is enabled.

## Build configuration

`mygo.json` declares the `mailto` URL scheme for macOS deep links.
Builds embed `internal/gmail/oauth-client.json` and fail when it is missing or invalid.
CI writes it from `MICA_OAUTH_CLIENT_JSON` before testing and packaging.
OAuth requests Gmail, OpenID, and Pub/Sub scopes. The embedded configuration supplies the Cloud project ID, and custom OAuth settings accept one too.
The OAuth file and the update signing private key are ignored by Git.
Release signing imports `MACOS_CERTIFICATE` into a temporary keychain; notarization uses `APPLE_API_KEY`, `APPLE_API_KEY_ID`, and `APPLE_API_ISSUER_ID` through `notarytool store-credentials`.

Real Gmail acceptance requires a Google test account.
